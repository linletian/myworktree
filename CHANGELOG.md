## v0.5.1 (2026-10-06)

Release focused on dsh 0.2.x support (issue #84), terminal WebSocket reliability (issues #80–#83, #86, #87), a beta prerelease channel off `develop`, and a round of UI/installer fixes — three of them found by the v0.5.1 betas themselves (issues #96, macOS overlay L2, alias-started daemon detection).

- **fix(install): the running-daemon Heads-up never fired for alias-started daemons** — found during the 0.5.0 → 0.5.1 upgrade-path manual test: the installer printed no "restart the daemon to pick up the new binary" warning even with a daemon provably running. Root cause: the detection ran only `pgrep -x myworktree`, but a process's comm is the basename of the path it was LAUNCHED through, so a daemon started via the `mw` symlink (the standard workflow) reports as `mw` — on a machine with six live daemons, `pgrep -x myworktree` matched zero. Detection now checks both the binary name and the resolved alias name (deduplicated), and the force-fallback `pkill` hint lists the alias form too.
- **fix(dsh-web): the overlay L2 check false-negatived on EVERY macOS instance, painting the "version too new / overlay not effective" bar over a fully-effective overlay** — live-reported on v0.5.1-beta.1 (dsh 0.2.0-rc.2, macOS): `version_supported` was `true` but `overlay_verified` stayed `false` for every instance. Root cause: `dsh web --dump-config` emits long scalars as `>-` FOLDED block scalars, wrapping the line AT the value's whitespace — and every macOS storages root lives under `~/Library/Application Support/…`, so the dump splits the root mid-path (`…/Library/Application` ⏎ `Support/…`) and `verifyOverlayDump`'s literal substring match on the raw root could never hit. Linux paths have no spaces, so the check only ever passed contiguously there and the failure was invisible in dev. The overlay itself was composed correctly the whole time — the other three rows (`directory-picker` / `directory-picker-browse` / `client-hmr`) matched on the same dump. Fix: the `storage-json` check now falls back to `blockContainsFolded`, a whitespace-stripped comparison over the row block — YAML folding only ever breaks at whitespace, so stripping both sides is the same check with the emitter's wrapping undone, and the block scoping keeps an unrelated row from satisfying it. Pinned by `TestVerifyOverlayDumpFoldedRoot` (a dump shaped exactly like the macOS report passes; the same dump with a different root still fails).
- **fix(ui): switching from a running web-ui instance to a stopped one of the same kind stacked the two iframes half/half (issue #96)** — reported live on v0.5.1-beta.1 with two dsh-web instances (A running, B stopped): selecting B showed B's stopped overlay on the top half while A's live iframe kept rendering on the bottom half, and switching to B from a TERMINAL instance did not reproduce. Root cause is the intersection of two deliberate designs: `selectInstance` only calls `prevRenderer.deactivate()` when the previous renderer is a DIFFERENT object (`prevRenderer !== renderer`), so a same-kind A→B switch never hid A's keep-alive iframe; and the stopped branch of each renderer's `activate()` shows the stopped overlay and returns early WITHOUT hiding the other cached frames — only the running path's `_showOnly(frame)` hides siblings. All three web-ui renderers shared the defect in different shapes: the `status === 'stopped'` early-return branches in `kinds/dsh_web.js` and `kinds/opencode_web.js`, and `_tick`'s not-running branch in `kinds/reasonix.js` (which hid only the active id's own frame). Each stopped/not-running branch now hides EVERY cached frame via `this._showOnly(null)` — with the selected instance stopped, nothing but the stopped overlay should be on screen (keep-alive is a visibility toggle, so the hidden frames keep their page state). Pinned by `TestWebRenderersStoppedSwitchHidesAllFrames`, which slices each renderer's stopped branch off the served assets and also pins the dispatch-side invariant (`prevRenderer !== renderer`) that makes the renderer-side hide-all necessary.
- **fix(install): the documented `NO_MODIFY_PATH=1` / `MYWORKTREE_BETA=1` env spellings are honoured** — the env value was compared literally against `"true"`, so `NO_MODIFY_PATH=1` (the spelling the header comment and `--help` have always documented) silently failed to skip the rc-file PATH edit; only `--no-modify-path` or `NO_MODIFY_PATH=true` worked. Both flags now normalize `1`/`true`/`yes` after arg parsing. Found during the beta rollout's own one-line-install testing.

- **fix(terminal): the tail rendered twice whenever a proxy stripped `X-Log-Offset`, because "nothing painted" and "painted but its offset is unknown" were the same cursor (issue #86)** — `GET /api/instances/log` answers with the ring-buffer tail and carries that tail's end offset in `X-Log-Offset`; `loadLog` painted the tail and advanced `logCursor` / `ttyOffset` only inside `if (Number.isFinite(next) && next >= 0)`, so when a reverse proxy dropped the header BOTH cursors stayed at the `-1` sentinel. That sentinel means "nothing is painted — send me the tail", which is exactly what the two transports then did: `startSSE` and `connectTTY` omit `since` for a non-positive cursor, `handleInstanceLogStream` answered the omitted `since` with `Tail(id, 64*1024)`, and `completeHandshake` replayed the same 64 KB as binary frames, so the bytes the browser had just painted landed a second time under itself. The two unknown-cursor states are now named and distinct. **`CURSOR_UNKNOWN` (-1)** — nothing painted: `since` stays OMITTED and the server's tail default applies, byte-for-byte today's behaviour (and still never `since=0`, the #81 oldest-64KB symptom). **`CURSOR_FOLLOW_LIVE_END` (-2)** — the screen IS painted and only its end offset is missing: the client sends the sentinel explicitly and the server sends NOTHING, the SSE stream emitting one empty `log` frame carrying the live head and then only newly produced data, the WS handshake emitting no binary frame at all, publishing `{"type":"sync","offset":<head>}` and subscribing. Each handler branches on `-2` EXPLICITLY, ahead of its `since < 0` tail branch, because `parseInt64Default` passes any negative value through untouched — a `-2` that fell into the tail branch would behave exactly like the omitted `since` that caused this bug. `Manager.EndOffset` is new: `Tail(id, 0)` in every respect that matters (same running-map lookup, same kind delegation with tail semantics, same cursor clamps, `0` for a non-running instance exactly as `Tail` returns `("", 0, nil)`) except the zero-length read — `RingBuffer.Tail` short-circuits `n <= 0` to its head, so a stripped-header connect no longer pays for a 64 KB copy it immediately throws away; `Kind.ReadLogs` now states that a tail read must carry its cursor even at `maxBytes == 0`, and the client-side constant mirrors the server's `sinceFollowLiveEnd` so the two cannot drift. Accepted trade-off, documented accurately at both call sites, because the honest version is worse than it first sounds. The window that self-heals is the one AFTER the head read (on the WS, head → `SubscribeOutput`; on SSE there is none, because the poll loop reads from the published cursor). The window this mode OPENS is the one BEFORE it: the client painted `GET /api/instances/log`'s tail up to some head `H1`, the sentinel publishes `H2 >= H1`, the client adopts `H2`, so `[H1, H2)` is in no replay, no painted body and no live frame — and because the cursor now sits past it, no reconnect re-requests it. Those bytes are permanently gone from that client's screen: the `loadLog()` → `connectTTY` hop in milliseconds, but 5 s + 500 ms of output — real lost lines — when the WS handshake times out and SSE is the fallback. Closing it would need the client to know `H1`, which is exactly the number the stripped header took away, so the choice stays duplicate-the-tail or lose-a-window, and losing the window is the one that keeps the screen readable. `GET /api/instances/log` (non-streaming) returns **400** for `-2` instead of falling into its tail branch, because the tail is the sentinel's opposite and a silent inversion there would resurrect this bug invisibly. The painted-then-stripped claim is now gated on CHARACTERS REACHING THE SCREEN, not on a terminal existing: `writeSanitizedTerminalOutput` returns the number of CHARACTERS it actually wrote (`.length`, UTF-16 code units, NOT bytes — 0 when sanitizing emptied the input), a value consumed only as a `> 0` boolean gate and never for byte accounting, and `loadLog` takes the sentinel only above zero, so an empty tail — or one consisting only of escape sequences the sanitizer strips — keeps `CURSOR_UNKNOWN` and both transports keep asking for the tail. That was a measured regression against HEAD: a brand-new instance with an empty ring behind a header-stripping proxy, printing one line just after the load, showed that line on HEAD and lost it here — issue #80's symptom, adjacent to the very fix that caused it, and free to avoid since an empty tail has nothing to duplicate. The zero-cursor non-goal's justification is now conditioned on the header being truthful, because the sentinel's whole premise is that it is not: a fabricated `0` over a non-empty ring does bring the duplicate tail back, and no client-side rule can tell that from a genuine head of 0 without a second, independently sourced length — the exact datum the proxy is already lying about. Review follow-ups that were real: the first cut declared `const CURSOR_UNKNOWN` at top level in BOTH `kinds/pty.js` and index.html's inline block, and since every script here is a classic script sharing ONE global lexical environment the second one would have thrown `SyntaxError` and killed the entire application script — a static shell and no terminal, on every page load. `kinds/pty.js` now owns a prefixed `PTY_CURSOR_UNKNOWN`, publishes nothing, and declares no follow-live-end constant (nothing in that renderer ever assigns one); the numbers are held together by tests instead of by load order. `loadLog` also sets the sentinel only AFTER the paint block and only if the paint actually ran — a cursor is a claim about screen content, and an unpainted session that asks for no replay never sees the tail at all. Pinned server-side by `TestHandleInstanceLogStream_FollowLiveEndServesNoReplayThenOnlyNewBytes`, `TestHandleInstanceLogStream_OmittedAndRealSinceKeepTodaySemantics`, `TestHandleInstanceTTYWS_FollowLiveEndReplaysNothing`, `TestHandleInstanceTTYWS_FollowLiveEndOnEmptyRingPublishesZero`, `TestHandleInstanceTTYWS_FollowLiveEndOnStoppedInstanceCloses`, `TestHandleInstanceTTYWS_FollowLiveEndReadFailureClosesConnection`, `TestHandleInstanceLogStream_FollowLiveEndOnStoppedInstancePublishesZero`, `TestHandleInstanceLogStream_FollowLiveEndOnNonCapturingKindNeverEchoesTheSentinel` (the wire-level pin for `EndOffset`'s `off < 0` clamp: a leak publishes `next:-1` and the client re-sends the sentinel forever), `TestHandleInstanceLog_RejectsFollowLiveEndSentinel`, `TestFollowLiveEndSentinelAgreesAcrossTheWire` (the `-2` has no compiler between `internal/app/app.go` and the browser, and it now also fails if `kinds/pty.js` ever re-declares an unprefixed `CURSOR_*`) and `TestManager_EndOffset*` in `internal/framework`; client-side by eight new `node --test` cases that drive `loadLog` → `startSSE` / `connectTTY` on ONE sliced session against a fetch that can strip the header (the eighth added by the review follow-up commit, pinning the sentinel check that reads BOTH sibling cursors), that cover the unpainted session and the `since=0` rule, and by a scope guard that collects the top-level declarations of every non-vendor classic script plus the inline block and fails on any name two of them declare — verified to go red against the colliding version before it was fixed.
- **fix(terminal): a half-open WebSocket was treated as alive, so a selected instance never reconnected (issue #83)** — after a laptop sleep, a network switch or a proxy idle timeout, a terminal tab could sit on a frozen screen while keystrokes vanished without any feedback. Root cause: `hasLiveTTYConnection` was purely instantaneous (`ttySocket` set, `readyState === OPEN`, `ttyState` in `HANDSHAKING`/`READY`) — none of the four conditions carried a clock — and a half-open TCP socket keeps `readyState === OPEN` indefinitely without ever firing `onclose`, so a dead-but-OPEN socket answered "live" forever. Everything downstream re-affirmed it: the 2 s poll's `refresh()` → `reconcileTerminalSessions()` → `ensureTerminalLiveTransport()` returned true on the SAME check every tick (fixing only `activate()` would be overridden by the poll), `activate()` early-returned over a stale xterm buffer, and keystrokes were swallowed because `term.onData` gates on `readyState === OPEN` and `ws.send()` does NOT throw on a half-open socket — so the HTTP input fallback was never reached. Server side there was no read deadline anywhere on the path, so the handler goroutine, the reader goroutine, the fd and the `ttyClients` entry leaked for the life of the daemon. And neither direction had a heartbeat: the server replied to pings, but browsers never send RFC 6455 pings, so that branch was dead for the browser. Fix — server (`internal/ws` + `internal/app`): `Conn.WritePing` added beside `WritePong` (the opcode and `writeFrame` primitive already existed); `handleInstanceTTYWS` became a thin mux wrapper over `handleInstanceTTYWSLiveness(w, r, pingInterval, readDeadline)` — the intervals are parameters, not mutable package state, so `t.Parallel` tests can compress the windows without racing (the reason package-level override vars were rejected); the reader goroutine arms `ttyReadDeadline` (**45 s**) before EVERY `ReadMessage`, so a silent peer's read times out, the goroutine returns, `msgChan` closes, and the EXISTING `case msg, ok := <-msgChan: if !ok { return }` arm unwinds the handler through its existing defers — no second exit path, and a read deadline is independent of `net.Conn`'s write deadline so it cannot disturb the writes; a `ttyPingInterval` (**10 s**) ticker (stopped via `defer`, the `handshakeTimer` pattern) writes BOTH an RFC 6455 ping — the browser's network stack auto-replies Pong, refreshing the read deadline, so a healthy connection is never reaped — AND a TEXT `{"type":"ping"}` frame, the only heartbeat browser JS can observe (`onmessage` never fires for control frames); a client-sent `{"type":"ping"}` is parsed like `isResize` and answered `{"type":"pong"}` with `continue` BEFORE the `SendInput` fallthrough, so the probe is never typed into the user's shell (same accepted collision as `{"type":"resize",...}`). - **fix(terminal): every WebSocket reconnect re-appended the last 64 KB of output under the live screen (issue #87)** — a network blip, a proxy idle timeout or a laptop sleep/wake duplicated or garbled the terminal: `ws.onclose` reconnects after 5 s without clearing the screen, while `completeHandshake` unconditionally replayed `Tail(id, 64*1024)` to EVERY connection, so the newest 64 KB landed under whatever the terminal already showed. Root cause: the WS handshake had no offset contract — the connect URL carried only `id`/`token`, the handshake threw away `Tail`'s end offset via `_`, and the client's `logCursor` served only the SSE path. Fix: the handshake gained a cursor round-trip. `GET /api/instances/tty/ws` accepts an optional `since` (absent/garbage → `-1` → tail, unchanged); `completeHandshake` — which reads the outer `since` instead of taking a parameter — replays `Tail` for the sentinel and otherwise loops `ReadSince(id, cursor, 64*1024)` until caught up, **streaming every chunk straight to the socket as it reads it** instead of retaining one — so the **whole delta is delivered** and the published offset is the end of the **last chunk actually written** to that socket, never an offset over bytes the client never received **and could still receive** — the two deliberate exceptions publish the ring's head, a path that writes nothing (no last chunk to name) and a closed ring whose buffer is gone (head is truthful because those bytes are permanently undeliverable) (retaining only the newest chunk delivered a replay *behind* the cursor it published, silently stranding everything older in the delta; and a single capped `ReadSince` would strand a 64 KB-behind-head cursor whose skipped bytes no later reconnect would ever re-request); peak memory stays ~64 KB — one chunk — regardless of the ring cap. One handshake replays at most 8 MB (`ttyHandshakeReplayBudget`, counted in bytes already written and checked before the next read so no further read is issued once spent), and anything beyond it is **deferred to the next reconnect** — the published cursor stays at the last chunk written, so the remainder sits ahead of it and comes back byte-for-byte — never skipped. The deferral has a price worth stating: ring caps are 16–256 MB, so a client whose cursor is far behind can need up to 32 reconnects to converge, and until it reconnects the deferred bytes stay undelivered on a socket that still looks healthy (the replay lands in xterm.js `scrollback: 10000`, so it is the older replayed content that scrolls out, never the live output that follows it). There is deliberately no write deadline on this path — the handshake is not yet subscribed to the output stream, so a blocked write does not stall the pump, and a wall-clock deadline would livelock a slow-but-progressing consumer that a byte budget merely resumes on the next reconnect. Output produced between the last chunk written and the live subscription sits behind the published cursor and is re-requested by the next reconnect — self-healing contiguity, not absolute coverage. After the replay the server emits a TEXT control frame `{"type":"sync","offset":N}` — even when the replay was empty, 0 being a legitimate cursor — and the client latches it per connection: `ttyOffset` becomes writable only after the `sync` frame, advances by the wire byte count of every live binary frame, survives `ws.onclose`, and goes back out as `since` on reconnect; `RingBuffer.ReadSince` supplies the silent stale-cursor clamp for free; on a zero-progress first read the handshake consults `Tail` for the real head, so a cursor exactly at head replays nothing stale while a cursor past head degrades to the first-connect tail instead of echoing the client's own number back as authoritative. The caught-up exit after at least one delivered chunk publishes that read's own `next` instead of leaving a zero: on a CLOSED ring `ReadSince` answers `("", head, nil)` while `since < head`, so the zero had been a cursor the ring never held and every such reconnect was thrown into a full tail re-replay — the truthful-`sync` half of this fix. ## v0.4.2 (2026-08-14)

Release focused on the Opencode native web UI integration, iframe renderer hardening, and README refresh.

**Opencode web UI — native integration**: each opencode instance now embeds the official opencode SPA via a same-origin reverse proxy at `/__opencode/<id>/`, with single-worktree isolation enforced by an in-memory `ScopeTracker` plus a UI guard that hides cross-worktree switch entries (project switch / add-project / open-project) and normalizes the localStorage server list to a single server, an `opencode --version` advisory gate (1.18.x) with DOM-anchor / visibility checks reported via `postMessage`, and a persistent in-panel warning bar for out-of-scope / hiding-not-effective states. The reverse proxy injects the unified `cfg.AuthToken` as Basic auth (`OPENCODE_SERVER_PASSWORD` per-instance = `cfg.AuthToken`, dropping the previous per-instance random password), so one token works for both the parent UI and the embedded server. The legacy deep session link that blanked the SPA is replaced by the full-page embed; SPA URL/Worker are rewritten at the proxy to keep the upstream unaware of its mounting path. New `Kind/Extra` fields on `state.json` (values: `pty` / `opencode-web` / `reasonix`); `password_set` is removed from `/api/instances/<id>/opencode` (always `true` previously, no frontend consumer). Design, threat model, and review checklist in `docs/ARCHITECTURE.md` §8; decision record in `docs/plans/opencode-native-ui/WORKTREE-ISOLATION.md`; post-mortem in `docs/plans/opencode-native-ui/DEBUG.md`.

**Reasonix iframe renderer hardening (merge of main → feature/opencode-native-ui)** — the v0.4.0 reasonix web-UI feature is now implemented as a third `framework.Kind` (`internal/instance/reasonix/kind.go`) inside the opencode-native-ui kind architecture, replacing the pre-refactor `internal/instance/manager.go` integration. All v0.4.0 reasonix behaviour is preserved: `/rx/<id>/` reverse proxy (token cookie + HTML URL-prefix rewrite), independent loopback listener with `web_url` (cross-origin, issue #44) and same-origin fallback for TLS/network listeners, sidebar-toggle injection, SSE streaming, CLI version gate (1.22.0), per-instance Start lock, state-dir cleanup on stop/restart/delete, shutdown `StopAllKind("reasonix")`, and re-attach of live serve processes on daemon restart (`RestartSurvivor`). Frontend: a dedicated Reasonix modal tab and `kinds/reasonix.js` renderer (per-instance iframe keep-alive across tab switches, issues #53/#54/#55). Tag semantics (`tag.Env` / `preStart` / `Command` / `Cwd`) restored for all kinds — a regression of the framework refactor that had left tags inert at instance start. `state.json` `kind` values are `pty` / `opencode-web` / `reasonix` (empty means `pty`).

### Breaking changes

- **`state.json` schema: `log_path` field removed** — external tooling that reads instance state files must drop the `log_path` field. Old state files continue to load cleanly (the field is silently ignored by JSON decoding). See `docs/ARCHITECTURE.md` §3.2.

### Highlights

- **In-memory ring buffer for PTY logs** — replaced per-instance on-disk log files with a bounded ring buffer (default 32 MB per instance, hard ceiling 256 MB, total budget capped at 25% of system RAM). Eliminates the 100,000× write amplification caused by the old `enforceMaxLogSize` loop. No more disk I/O from PTY logging on the steady state.
- **Bounded adaptive sizing** — new `LogBufferBytes` config knob overrides the per-instance cap (clamped to 16–256 MB). When unset, the cap is `clamp(available / 16, 16 MB, 256 MB)` sampled via gopsutil with a 60 s cache to amortize syscall cost across batch starts.
- **Startup cleanup** — `Manager.PurgeOrphanLogFiles` removes dead `.log` files left behind by the old code path on the first start of the new binary.
- **Budget-exceeded UX** — when a new instance would push the global buffer budget past 25% of system RAM, the HTTP/MCP API returns `503 Service Unavailable` with a structured `log_buffer_budget_exceeded` body. The dashboard surfaces this as a modal with used/limit numbers and a hint to close other tabs.
- **Hot-path redesign for heavy TUI workloads** — `pumpLogs` no longer acquires `stateMu` per 1024-byte PTY chunk; the ring buffer pointer is pre-fetched once and the per-chunk lookup is a single `atomic.Pointer.Load`. The ring buffer's backing slice is allocated eagerly so the first Write never blocks on a 32 MB malloc. A new `WriteString` path avoids the `[]byte(chunk)` conversion that would otherwise happen on every chunk.
- **Daemon resource monitoring** — the resource stats API (`GET /api/instances/stats`) now includes the mw daemon process itself in global totals (`daemon_cpu_percent`, `daemon_memory_bytes`). The UI displays a dedicated "mw daemon" row so users can distinguish daemon overhead from instance resource usage.
- **Ring buffer usage reporting** — per-instance stats now expose `memory_buffer_bytes` (actual usage) and `memory_buffer_cap_bytes` (pre-allocated capacity). The UI memory column shows the combined `RSS + buffer_used` with a `buf used/cap` annotation for active buffers, giving users visibility into per-instance buffer memory cost.
- **Sidebar GitHub link** — main workspace row now shows a small GitHub Mark icon to the right of the project name when `git remote` resolves to `github.com`; clicking opens the canonical `https://github.com/<owner>/<repo>` URL in a new tab. Source of truth is a new `github_url` field on `GET /api/main`, computed via the new `gitx.GitHubURL` helper (prefers `origin`, then falls back to iterating `git remote`; normalizes SCP / HTTPS / `ssh://` forms; strips `.git`). GitHub Enterprise and non-GitHub remotes are intentionally not surfaced.
- **Unified auth token for opencode-web** — `OPENCODE_SERVER_PASSWORD` now equals `cfg.AuthToken` for every opencode-web instance (replacing per-instance random passwords). The reverse proxy at `/__opencode/<id>/*` injects Basic auth with the same token. `state.json` no longer carries a per-instance `password` field. Threat model and review checklist in `docs/ARCHITECTURE.md` §8.
- **Graceful goroutine lifecycle** — `Manager` gains `instCtx` + `instWG`. `Restart` / `Delete` cancel the instance context and `Wait()` for `pumpAndWatch` / `opencodeHealth` / `wait` (opencode-web) or `pumpLogs` / `wait` (PTY) to drain before returning, so callers never observe stale goroutines touching `m.buffers[id]` / `m.ocRT[id]` after a lifecycle transition. `Stop` keeps its existing fire-and-forget semantics.
- **In-memory health-fail counter** — `opencodeHealth` no longer writes `_health_fail_count` to `Extra`; the counter lives in `Manager.ocRT[id]` (atomic Int32, cleared on restart). Reduces store writes from "every probe" to "every successful listen-address parse".
- **`UpdateExtra` is now merge + retry** — preserves pre-existing keys (e.g., `worktree_abs`), retries on `ErrVersionConflict` so concurrent writers don't silently drop updates, and transitions `starting → running`.
- **`password_set` removed from `/api/instances/<id>/opencode` response** — was always `true` and no longer meaningful; no frontend consumer. See `docs/API.md` §5.10.
- **Text file preview** — click a file in the Changes panel to preview it with line numbers, a formatted view, and a diff view (including a synthetic diff for untracked files, with `quotePath` handled).
- **Branch divergence badge** — the sidebar now shows a diverge badge when a branch is ahead of / behind its upstream, backed by new API handlers and scheduled refresh.
- **`mw config regen`** — new CLI command to regenerate the config, plus per-request auth token reload so config/token changes take effect without a daemon restart.
- **Tags config directory** — open the tags config directory from the UI and use default tags out of the box.
