## 一、整体目的（这批改动在做什么）

新增第 4 种 instance kind `dsh-web` —— 把 DeepSeek Harness 的 `dsh web` 当作受管子进程嵌进实例标签页，跟 opencode-web / reasonix 平起平坐。配套的安全/数据姿态：

- **每实例一个独立 loopback origin**（SPA 客户端 API base 写死 `location.origin + '/api'`，所以同源子路径不可行）
- **共享 DSH_HOME**（凭据/设置不重配），但 `storage-json.root` 重定向到按 worktree 隔离的注册表目录
- **sessions 池保持共享**（终端裸跑 dsh 与 web 实例互通），越界只警告不拦截
- **远程模式（主监听非 loopback 或 TLS）** 走强制 token 门（`?token=` 或 `mw_token` cookie，strip 掉再转发上游；WS 升级同样校验）
- **缺依赖对话框**：npx 启动（pin 版本 + Setpgid 杀进程组）/ `npm install -g`（绝对路径 spawn）/ 取消
- **版本硬门 + advisory 区间** + L2 `--dump-config` overlay 校验
- **4 个新 HTTP API**：`GET /api/instances/dsh[?scope]` + `POST /api/instances/dsh[?launch|install]`

涉及 12 个修改文件 + 9 个新文件（新 `internal/instance/dsh_web/` 包 7 个 .go + 6 个 _test.go，新前端 `kinds/dsh_web.js`，新 `docs/plans/dsh-native-ui/{PLAN,TASK,FEASIBILITY,CROSS-PROCESS-SESSION}.md`）。`go build ./...` clean，`go vet ./...` clean，`go test ./internal/instance/dsh_web/... ./internal/app/...` 全过。

## 二、发现（按风险由高到低）

### 1. `handleInstanceDshInstall` 直接执行 `npm install -g`，无审计/限流/确认

`internal/app/app.go:1885-1910`：用 5 分钟超时跑 `npm install -g @deepseek-ai/dsh` + `npm prefix -g`，把绝对路径写进 worktree 状态。**风险**：

- 如果 myworktree 进程以 root 运行（容器/系统服务常见），会改全局 npm prefix，影响系统上所有用户
- 前端触发后只显示 "正在执行…"，无二次确认；任何能拿到 token 的客户端都能让守护进程跑任意 `npm install`
- 无并发互斥：两个标签同时点 "立即安装" 会跑两次 npm install
- 不会回滚：如果 `npm install` 半路失败 + 部分写入，已写入的文件不会清理
- 行为完全在 `CHANGELOG.md` 里说了，但缺一条用户可见的"此操作会修改系统 npm prefix"提示

**建议**：安装前给一个 `<dialog>` 二次确认（说明将改 npm prefix、需要写权限、需 ~30s），加进程内 mutex 避免并发，失败时记录已写入的文件清单。

### 2. 跨进程会话日志损坏 —— 已记录但用户没救生圈

`docs/plans/dsh-native-ui/CROSS-PROCESS-SESSION.md` 详细记录了 dsh 上游 bug：第二个 dsh 进程打开**正在被其他进程写入**的会话 → `session/end-seed` 无锁追加撞 seq → 日志永久损坏。文档里写"已损坏日志按用户要求保留原状，未做任何修复或进程操作"。

**风险**：在生产里，**我的**（myworktree 嵌入的）UI 打开共享池里终端正在工作的会话时，会把这个会话的日志写坏 —— 不只是"我自己"读不到，是**所有非写入者进程**都读不到。文档诚实承认了。

**建议**：哪怕是缓解，也应该在 myworktree 侧加一个"会话活跃性嗅探"（mtime + 进程归属探测），嗅探为活跃的会话在 UI 里灰掉打开按钮并显示"另一进程正在写入，打开会损坏日志"。文档里第 5 节也提到这是缓解方向。

### 3. `proxy.go:80-114`：代理 listener 死亡时静默吞错

```go
go func() {
    var serveErr error
    if cfg.TLSCert != "" && cfg.TLSKey != "" {
        serveErr = srv.ServeTLS(ln, cfg.TLSCert, cfg.TLSKey)
    } else {
        serveErr = srv.Serve(ln)
    }
    if serveErr != nil && !errors.Is(serveErr, http.ErrServerClosed) {
        // The listener died on its own (e.g. bind race); nothing to
        // do — the health loop / instance status will surface it.
    }
}()
```

**问题**：注释说"health loop 会 surface"，但 health loop 探的是**上游** `127.0.0.1:<upstreamPort>/`，不是代理 listener 本身。如果代理 listener 死了（比如 TLS 握手 panic、TLS 证书热更新后文件被替换）但上游还活着，health loop 一直 OK，iframe 用户拿到的是连接拒绝/502，没有 instance 状态变化。

**建议**：代理 listener 死亡时立即调 `p.MarkFailed("proxy listener died: …")` + 记录 error 级别日志。

### 4. `proxy.go:164-168`：ErrorHandler 在头已发出时不会真返回 502

```go
proxy.ErrorHandler = func(w http.ResponseWriter, req *http.Request, err error) {
    writeJSON(w, http.StatusBadGateway, map[string]string{"error": "dsh server unreachable"})
}
```

`httputil.ReverseProxy` 的 ErrorHandler 只在**还没写头部**时被调用；上游半路断（写了头但 body 没写完）就走 ErrorHandler，但 `writeJSON` 会因为 `w.WriteHeader(http.StatusBadGateway)` 在已经发过头的情况下被忽略（Go stdlib 会 warning，但用户端拿到的是截断响应，不是 502）。这是 stdlib 反代的经典陷阱。

**影响**：在 SSE/WS 通道里断流，iframe 可能卡在"半收"状态。**建议**：观察下上游断流场景的实际表现；如果用户端经常见到白屏/卡死，把上游也设为 read/write deadline 强制关连接。

### 5. `app.go: handleInstanceDshInfo`：用 `r.Host` 推导 iframe_src 的 host，客户端可控

`internal/app/app.go:1750-1762`：

```go
if proxyHost == "0.0.0.0" || proxyHost == "::" {
    if h, _, herr := net.SplitHostPort(r.Host); herr == nil {
        proxyHost = h
    } else {
        proxyHost = r.Host
    }
}
```

**问题**：当代理绑 `0.0.0.0`（非 loopback 远程模式），iframe src 的 host 从请求 `Host` 头派生。任何已认证客户端都能让前端渲染指向任意 host 的 iframe —— 如果该 host 真能路由到 dsh 上游端口，浏览器会去拉（不算越权，但是 **URL 拼接/钓鱼辅助**；配合恶意 DNS 引导点击，可做成"看似是 myworktree 资源但其实指向攻击者"）。

**风险等级**：低 —— 客户端必须已经过 token 认证，且浏览器侧有同源策略保护。**建议**：把 host 锁成 main listener 配置里的 host（`cfg.ListenAddr`），不用 `r.Host`。

### 6. `dsh_web.js:198-264`：polling 在 missing_dsh 路径上彻底停了

`_startPolling` 在检测到 `data.missing_dsh` 后调 `_showMissingDialog(id, missing_dsh)` 然后 `return`，**没有 setTimeout(tick, POLL_MS)**。如果用户点 "取消" 关掉对话框但**不删实例**，polling 就停了，instance 也保持 failed —— 用户得手动点 Refresh 一次才能再次看到对话框。

**建议**：对话框关闭时（或 onCancel）恢复 polling。

### 7. `driver.go:218`：`restrict.yml` 用 `0o644`

`os.WriteFile(overlayPath, buildRestrictOverlay(storagesRoot), 0o644)` —— overlay 文件包含 worktree 路径和注册表根路径。如果 DataDir 跑在多用户系统（虽然不常见），路径会泄露。

**建议**：`0o600`，和 `launch.json` 一致。

### 8. `app.go: handleInstanceDshInstall` 的失败响应：`npm install` 输出可能很大

`internal/app/app.go:1900`：

```go
out, err := exec.CommandContext(installCtx, "npm", "install", "-g", "@deepseek-ai/dsh").CombinedOutput()
if err != nil {
    writeErr(w, http.StatusBadGateway, fmt.Errorf("npm install failed: %w: %s", err, strings.TrimSpace(redact.Text(string(out)))))
    return
}
```

`redact.Text` 只剥 token、不剥路径/email —— 算预期行为，**但**安装时若用户 npm 配置了私有 registry + 凭证，错误里可能回显带凭证的 URL（npmjs 自己的错误格式）。建议加一次 `strings.Contains` 截断（看 `bootstrap.go:truncate` 的 300 字符模式），避免给前端发几 MB 错误。

### 9. `app.go:1740-1748`：本地模式下 `iframe_src` 优先用 `b.IframeURL`，但 `b.IframeURL` 是 spawn 时写死的

`handleInstanceDshInfo` 里 `resp["iframe_src"] = b.IframeURL`，但 `b.IframeURL` 是在 driver `pumpAndWatch` 解析就绪行后立刻写入的，形如 `http://<ph>:<pp>/`（proxy host:port）。如果实例启动后**代理 listener 死掉又没被 closeProxy 关掉**（见第 3 点），前端拿到一个死端口的 URL，没法刷新。**建议**：本地模式下，proxy listener 死了之后，**主动把 blob.IframeURL 清空**触发前端回退到"启动中"。

### 10. `CHANGELOG` 把"spec"和"implemented"两条并列放在 Unreleased

`CHANGELOG.md:5-12` 5 条新条目，4 条 "feat/fix" + 1 条 "fix"。从 reviewer 角度：建议发布时合并成 1 条 `feat(instance): dsh-web kind (DeepSeek Harness web UI embed)` + 子条，PR 描述里能看到"分 5 个 PR 提交"是 review trace，但 changelog 用户层面是单一 feature。

### 11. `index.html` diff 跨了 11 个不相关分支（terminal / opencode-web / reasonix 互斥扩展、pty tags 过滤、destroyFrame 名单等）

`internal/ui/static/index.html:2618-3020` 这段为了支持 dsh-web 改了一处"凡是 web UI 都要做这个"的循环（`ptyTags = state.tags.filter(t => t.id !== 'opencode-web' && t.id !== 'dsh-web')`、`stoppedInst.kind === 'opencode-web' || ... === 'dsh-web'` 等），下一种新 web UI 进来还要再改这些地方。**建议**：抽一个 `WEB_UI_KINDS = ['opencode-web', 'reasonix', 'dsh-web']` 常量。

### 12. `app_dsh_test.go:59`：`dshTestInstance` 重复了 `store.ManagedInstance` 的字段（与 opencode_web 的同名测试 helper 高度相似）

`internal/app/app_dsh_test.go:59-69`：

## 附2：服务端 token 化归档（2026-08-16，issue #13 的回归修复）

- **回归现象（真机实测）**：portal / 登录态远程页面打开 dsh-web 实例时弹"远程访问需要认证"假警告，且 iframe 无 token 被代理 401。
- **根因**：`mw_token` 是 **HttpOnly** cookie——`document.cookie` 里 JS 永远读不到；portal/login 流程地址栏又没有 `?token=`。此前"前端从 cookie/地址栏取 token 拼 iframe URL"的方案在"cookie 登录态 + 无地址栏 token"场景必然失败。opencode/reasonix 的 iframe 是同源相对 URL，cookie 自动随请求带上，所以只有独立 origin 的 dsh-web 踩中。
- **修复**：`handleInstanceDshInfo`（位于 `withAuth` 之后，仅已认证客户端可达）在代理 token 门开启时**服务端自行**给 `iframe_src` 拼 `?token=<Proxy.AuthToken>`——读的是 proxy 自己的凭据（与 `checkToken` 校验的一致，而非 `cfg.AuthToken`，防止未来主 token / proxy token 分离时 URL 失效）；前端只做：识别服务端已拼 src（不重复拼、不警告）/ 地址栏 token 兜底 / 真无 token 才警告。代理仍校验 → 种 proxy-origin HttpOnly cookie → 302 到无 token URL，嵌入文档 `location.search` 不含 token（ARCHITECTURE §9 检查表不变）。
- **验证**：`TestHandleInstanceDshInfoTokenizesRemoteSrc`（cfg/Proxy 用不同值，钉死"读 Proxy"）+ `docs/plans/dsh-native-ui/dsh_web.test.mjs`（node --test，4 分支）+ `pr5-remote-e2e.sh` 第 6 节（URL parse 精确断言，LAN+TLS 全矩阵通过）。
