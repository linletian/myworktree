# iPadOS 输入与视口设计指导思想

**适用范围**：issue #116 及 v0.6 UI 的后续设计讨论与评审。
**文档性质**：设计原则，不是既有实现声明，不是新的开发计划或任务拆解。
**日期**：2026-11-04。

## 1. 核心原则

> **终端输入归应用，Web 输入归 Safari；归属由当前焦点决定，切换时明确交接，不做全局 pan 锁死。**

这里需要分别理解三个概念：

- **键盘遮挡**：软键盘覆盖了多少屏显区域；
- **pan**：Safari 为让聚焦输入框可见而移动可视窗口；
- **zoom**：页面缩放比例变化。

三者相关，但不是同一个问题，不能用一项全局补偿同时处理。

## 2. 产品目标

### 2.1 前台终端实例

myworktree 的 PTY 终端追求原始终端体验。前台终端输入激活时，应优先由应用处理软键盘适配，使终端的可用视口完整呈现在屏显区域内，不依赖 Safari pan 把终端主体移出屏显区域。

这里的“完整”指终端当前可用视口及其输入区域，不指一次性显示全部 scrollback。

### 2.2 普通 Web 输入组件

普通 Web 表单已有成熟的系统行为：输入框被遮挡时，Safari 按实际输入位置进行必要的 pan；输入框未被遮挡时，不进行多余移动。产品设计应利用这一能力，而不是重复实现或压制它。

### 2.3 iframe 内 Web UI

opencode、reasonix、dsh 等 iframe 内的输入由 iframe 与 Safari 协作处理。父页面不发明跨 iframe 输入定位协议，也不以父页面的终端避让规则干扰其原生行为。

## 3. 输入所有权矩阵

| 当前输入状态 | 设计归属 | 终端实例处理 | Safari 原生 pan |
| --- | --- | --- | --- |
| 前台 PTY 的终端输入光标激活 | 应用负责终端软键盘适配 | 只调整终端实例的可用视口，保持输入区域和终端主体可见；外壳不随键盘整体移动 | 尽量避免发生，不以自动 pan 作为终端体验的基础 |
| 本页普通 Web 输入组件获得焦点 | Safari 负责输入可见性 | 不因该输入框执行终端避让 | 允许并利用 |
| iframe 内输入组件获得焦点 | iframe / Safari 负责 | 父页面不干预 | 允许并利用 |
| 没有可编辑焦点，或没有确认的软键盘输入会话 | 沿用既定状态分类 | 不额外避让 | 不主动控制 |

判断依据不是“屏幕上是否显示终端”，而是“当前焦点是否属于前台 PTY 的终端输入宿主”。终端仍在背景中但用户正在重命名实例时，应归入普通 Web 输入，而不是继续持有终端输入所有权。

## 4. 普通 Web 输入的范围

本原则中的普通 Web 输入包括但不限于：

- 新建、重命名 worktree；
- 新建、重命名实例；
- 设置和其他本页表单；
- quick-keys 的粘贴 textarea；
- 其他 `input`、`textarea`、`contenteditable` 宿主；
- iframe 内 Web UI 的输入组件。

这些场景不应仅因为可编辑元素获得焦点，就自动套用 PTY 终端避让。

## 5. 焦点交接原则

输入所有权必须在焦点变化时明确交接：

- **PTY → 本页 Web 输入**：退出终端输入模式，把输入可见性交还 Safari；
- **PTY → iframe 输入**：父页面不干预 iframe 的系统行为；
- **Web / iframe 输入 → PTY**：只有前台 PTY 的真实终端输入宿主重新获得焦点后，才重新进入终端输入模式；
- **PTY A → PTY B**：以新前台终端为准，不保留旧实例的输入所有权；
- **PTY → quick-keys 粘贴输入**：按普通 Web 输入交接，不叠加应用终端避让与 Safari pan；
- **旋转、窗口变化、缩放、前后台切换**：重新确认当前输入归属，不将旧模式永久锁定。

非活动或隐藏的 PTY 不能仅因存在宿主而取得输入所有权。进入终端模式后如何同步其实例几何，是后续实现设计问题，不影响上述触发原则。

## 6. 设计边界

本原则明确不支持以下做法：

- 全局锁死 pan，使所有 Web 输入都失去 Safari 原生兼容能力；
- 通过 `scrollTo(0,0)`、反复写根 `scrollTop` 或反向 `transform` 与 Safari 争夺视口；
- 为了统一处理而重新把整个 `#app` 钉到 `visualViewport.height`；
- 对所有可编辑元素使用同一套终端遮挡补偿；
- 要求 iframe 上报内部光标或输入位置，才能使用系统键盘行为；
- 将 `vv.offsetTop` 简单叠加到现有终端 raw 算式，形成重复补偿。

PTY 模式的合理方向是尽量让终端输入区域在 Safari 产生自动 pan 之前已经可见，而不是事后再把页面抢回原位。该方向不构成对任何具体实现的授权。

## 7. 与 zoom 豁免的关系

页面已经处于缩放状态时打开软键盘，与用户正在进行双指缩放，是不同的产品场景。本原则不自动取消、也不自动保留某一项具体缩放策略，更不授权修改既有 zoom 豁免。

缩放状态下的终端体验需要独立评估和真机验证，不能通过全局锁 pan 或删除 zoom guard 一并处理。

## 8. 后续设计与真机评审口径

任何以本原则为依据的后续方案，至少应分别验证：

1. 前台 PTY 输入时，终端可用视口和输入区域完整可见，不依赖系统 pan 把终端移出屏显区域；
2. 本页新建、重命名等普通输入由 Safari 保证可见，不触发额外的终端避让；
3. iframe 内输入沿用系统行为，父页面无额外干扰；
4. PTY、普通 Web 输入、iframe 输入之间切换时，模式交接正确且无旧状态残留；
5. quick-keys 粘贴、横竖屏、窗口变化、缩放、前后台恢复等边界场景得到独立判定；
6. 使用真实 iPadOS 设备确认行为，Headless Chrome 不替代 Safari 的键盘、pan 或 zoom 证据。
